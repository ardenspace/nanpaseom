# Spec: 난파섬 세이브 연속성 정리 — 코드-열쇠 가장자리 묶음

## Product Picture

**누구를 위한 것.** 커뮤 공개 후 들어올 익명 플레이어. 계정·로그인 없이
쿠키와 세이브 코드로 진행을 이어간다.

**이미 서 있는 것 (이번 런의 출발선).** 세이브 코드는 이미 세션을
가리키는 열쇠(스냅샷 아님)라 "A에서 코드 → B에서 복원 → B에서 더 플레이
→ A로 복귀"는 지금도 같은 세션으로 이어진다. 타이틀 화면에는 "세이브
코드로 이어하기" 입구가 상시 노출돼 있고, redeem 은 무조건 대체 확인
다이얼로그를 거친다(조용한 갈아타기 없음 — 지난 런의 의식적 설계).

**남은 구멍 (이번 런이 메우는 것).**
① 대체 확인 다이얼로그가 경고만 하고 **현재 진행을 지킬 방법을 주지
않는다** — 갈아타면 지금 세션은 코드가 없는 한 영영 못 돌아온다.
② 재발급이 항상 같은 코드라 **유출된 코드를 죽일 방법이 없다**.
③ 코드를 한 번도 안 받은 플레이어는 쿠키가 소멸하면 진행을 잃는다 —
입구가 있어도 넣을 코드가 없다.
④ redeem 에 시도 제한이 없어 코드 공간(~1,390만)이 온라인 추측에 열려
있다 — 코드가 살아있는 세션 열쇠이므로 이제 세션 탈취와 같은 값이다.

**핵심 경험.** 언제, 어느 기기로 돌아와도 가장 최신 진행이 그대로 있다.
배포된 UI 안에서 진행을 **모르는 새** 버리는 경로가 없다 — 갈아타기는
경고와 탈출구를 거치고, 회전은 "이전 코드가 죽는다"를 명시한다. 남는
누수는 둘 다 의식적 수용이다: ③ 코드를 한 번도 안 받은 채 쿠키를 잃는
경우(넛지로 줄이되 차단은 아님), 그리고 옛 코드만 들고 있는 기기가
다른 기기의 회전으로 접근을 잃는 경우.

**스모크 시나리오.** 기기 A에서 플레이해 상태를 올린다 → 세이브 코드
발급 → 기기 B에서 코드로 복원하고 더 플레이한다 → 며칠 뒤 기기 A(쿠키)로
복귀한다 → 어느 기기에서든 가장 최신 진행이 보이고, 아무것도 되돌아가
있지 않다. 갈아타기 순간에는 경고와 탈출구(현재 진행의 코드)가 보인다.

## Requirements

각각 독립 검증 가능:

1. **명시적 회전**: 회전 액션 호출 시 새 코드가 발급되고 이전 코드는
   즉시 무효(redeem 404 — 그 문자열이 훗날 재민팅되기 전까지). 이전
   코드와 새 코드가 동시에 유효한 순간이 없다. 회전은 배포된 UI에서
   플레이어가 도달할 수 있다(API 전용 아님).
2. **발급 idempotent 유지**: 기존 발급 액션은 계속 "있으면 기존 코드
   반환" — 적어둔 코드는 회전 전까지 유효. (from knowledge.md — 기존 계약 유지)
3. **redeem 시도 제한**: 직결 IP당 시도 횟수 제한 초과 시 429 + 솔직한
   시스템 톤 문구. 수치·문구는 rules YAML.
4. **갈아타기 탈출구**: 기존 대체 확인 다이얼로그에 "현재 진행의 세이브
   코드 받기" 경로를 추가한다 — 갈아타기 전에 지금 세션의 코드를 손에
   넣을 수 있다. 기존의 **무조건** 확인 동작은 그대로 유지한다(진행
   유무로 다이얼로그를 건너뛰지 않는다 — B4).
5. **기존 연속성 동작 pin**: 타이틀 상시 이어하기 입구와 무조건 대체
   확인이 이번 런의 변경으로 깨지지 않음을 테스트로 고정한다(신규 기능
   아님 — 회귀 방지).
6. **코드 뽑기 넛지**: 코드를 발급한 적 없는 세션에 의미 있는 진행이
   쌓이면 "진행을 지키려면 세이브 코드를 받아두세요" 넛지를 띄운다.
   판정은 서버 진실(B2b `has_save_code`) 기준. 트리거 임계값·문구는
   프론트 톤 홈에 산다(컴포넌트 인라인 금지). 최소 관측 계약은 B5.
7. **INSECURE_COOKIE 허용목록 반전**: `NANPASEOM_INSECURE_COOKIE` 는
   허용목록 값(`"1"`/`"true"`, 대소문자 무시)일 때만 Secure 생략. 그 외
   모든 값(오타 포함)은 Secure 유지. (from knowledge.md — 런 리뷰 보류분)
8. **strike.register 시끄럽게**: 전제(존재 확인된 세션) 위반 시 조용한
   무동작 대신 즉시 실패. 모든 기존 호출부가 전제를 만족함을 테스트로
   pin — 플레이어에게 보이는 동작은 불변(이 실패는 도달 불가여야 한다).
9. **프론트 테스트 러너 도입**: vitest(급)를 도입하고 B4 탈출구·무조건
   확인 동작과 B5 넛지 판정 로직을 결정적 테스트로 pin. 훅 추출로
   옮겨지는 `/turn` 401 자동 복구 경로(클라이언트가 새 세션으로 진입하는
   유일한 지점 — B5 재노출 조건과 맞물린다)도 회귀 pin 대상. UI
   스냅샷/E2E는 범위 밖. 테스트 파일도 문구 규칙(Conventions 3)을
   따르므로 기존 하드코딩 게이트가 계속 그린이어야 한다.
10. **스모크 보존**: 위 변경 후에도 기존 게이트(pytest/check_yaml/
    하드코딩 grep) 전부 그린 + 프론트 타입체크·빌드(`bun run build`)
    그린 + 신규 프론트 테스트 그린. 수동 스모크는 **새로 빌드한 dist**
    에 대해 수행한다(`GET /` 와 `/assets/*` 가 그 산출물을 서빙하므로
    낡은 번들로 확인하는 사고 방지). Product Picture의 스모크 시나리오를
    사람이 수동 확인하고 그 결과를 `.talpi/manual-check.md` 에 기록.

## Out of Scope (v1)

- bearer 쿠키 서명 (신원 모델 불변 — 다음 런 이후) (from knowledge.md, ADR 0034)
- 대화 기록 보존 정책 / 플레이어 삭제 경로 (데이터 오너십 별건) (from knowledge.md)
- 익명 대량 민팅 + 밴 우회 방어 (from knowledge.md)
- 실제 배포 (서버/도메인/HTTPS/프로세스 매니저/Cloudflare) — 다음 런 (from knowledge.md)
- 계정/로그인 도입
- warning 응답 시 이전 choices echo (이전 런부터 범위 밖 승계) (from knowledge.md)
- 코드 회전 유예 기간 / 소각 목록 (Reversibility Ledger 참조)
- 응답 지연·온보딩 개선 (Act 1에서 전반적 걱정으로 분리)
- UI 스냅샷/E2E 테스트, CI 워크플로 신설 (게이트는 로컬 명령)
- bootstrap 호출 시점 이동(페이지 로드 시 eager bootstrap) — 방문자마다
  세션 민팅 + 오프닝 LLM 콜을 유발하므로 명시적 비목표

## Simplicity Zones

- **동시 플레이 충돌**: 두 기기가 동시에 같은 세션으로 보내는 경우 진짜
  동시성 제어 없음 — 마지막에 쓴 쪽이 이긴다. 시나리오는 번갈아 쓰기다.
- **회전 UX**: 정교한 관리 화면 없음. "새 코드 발급 = 이전 코드 즉시
  무효" 한 줄 규칙 + 최소 UI.
- **무차별 대입 방어 수준**: 앱 레벨 단순 방어까지만 — 단일 프로세스
  메모리 카운터. 기록된 한계: 재시작 시 리셋, 분산 공격에 약함, 직결
  IP 기준이라 프록시 뒤에선 무의미(배포 런에서 재검토 필수 — Ledger).
- **무효화된 코드의 UX**: 회전으로 죽은 코드는 오타·미지의 코드와 동일한
  404 문구 — 구분하지 않는다 (구분하려면 코드 히스토리 필요, 무유예
  결정과 일관).

## Boundary Contracts

### B1: 회전 액션 — POST /save-code/rotate

- 신원: 해석기(resolve_session) 통과분만. 거부 시 401 + rules/identity.yaml
  `no_session_message` (발급과 같은 결). 세션 생성/쿠키 발급 없음.
- 밴 세션: `200` + `{"status": "banned", "ban_reason": ...}` (발급과
  동일 결) — 회전 없음.
- 성공: `{"status": "ok", "save_code": "<WORD-XXXX>"}` — 새 코드. 형식은
  기존 `save_code.py` 정의 불변.
- 관측 계약: 성공 응답 이후 이전 코드는 redeem 404, 새 코드는 redeem
  성공. 이전 코드와 새 코드가 동시에 유효한 순간이 없다. 연속 호출은
  매번 새 코드 (idempotent 아님 — 발급과 구분).
- 코드 미발급 세션(save_code NULL)에서의 호출: 첫 코드 민팅으로 성공
  (무효화할 이전 코드가 없을 뿐, 에러 아님).
- 무효화된 코드 문자열은 소각되지 않는다 — 이후 민팅에서 재사용될 수
  있다(확률적으로 희박, Ledger 기록).
- 프론트 어포던스: 채팅 화면의 세이브 코드 보기 경로에서 회전에 도달할
  수 있고, 회전 UI는 "이전 코드는 더 이상 쓸 수 없다"를 명시한다. 같은
  화면의 기존 문구("다시 확인해도 코드는 바뀌지 않습니다")는 회전 도입과
  모순되므로 함께 개정한다.
- 다른 기기/탭이 이미 화면에 띄워 둔 옛 코드는 회전 후에도 그대로 보일
  수 있다(스테일 표시) — 서버 계약은 지켜지며 이 표시 불일치는 감수한다.

### B2: 발급 — POST /save-code (기존 계약 pin)

기존 계약 그대로: 401(무신원) / banned / ok(기존 코드 있으면 그대로
반환, 없으면 민팅). 회전 도입 후에도 이 idempotency가 깨지지 않음을
테스트로 pin. (from knowledge.md — 지난 런 계약)

### B2b: 세션 진입 응답 — has_save_code 추가

불리언 `has_save_code`(이 세션에 유효한 세이브 코드가 있는지)를
**세션 진입 wire shape 전체**에 추가한다 — `POST /session/bootstrap` 과
`POST /save-code/redeem` 의 성공 응답(new/resumed)은 같은 shape 를
공유하므로 둘 다 이 필드를 싣는다. 가산적 변경(기존 필드 불변), 세션
식별자는 여전히 본문에 싣지 않는다.

값이 낡지 않게 하는 규칙(넛지 판정의 권위):
- 진입 응답의 값이 그 시점의 진실이다.
- 세션 도중 발급(B2)·회전(B1)이 성공하면 클라이언트는 그 즉시
  `has_save_code` 를 참으로 간주한다 — 두 응답 모두 코드를 돌려주므로
  추가 왕복이 필요 없다.
- 이 두 경로 외에 세션의 코드 보유 상태가 바뀌는 경로는 없다.

### B3: redeem — POST /save-code/redeem + 시도 제한

- 기존 계약 유지: 형식 위반/미지의 코드/무효화된 코드 404(동일 문구),
  밴 세션 재바인딩 없음, 성공 시 쿠키 재바인딩, 성공 다이얼로그 경유.
- 신규: IP당 시도 제한. IP는 **직결 연결의 원격 주소**
  (`request.client.host` 상당) — `X-Forwarded-For` 등 클라이언트 제공
  헤더는 신뢰하지 않는다. 초과 시 `429` +
  `{"status": "error", "message": <rules YAML 문구>}`.
- 집계 규칙: **엔드포인트로 들어온 모든 시도가 집계된다** — 형식 위반,
  404, 성공 모두 포함. 성공이 카운터를 리셋하지 않는다(유효 코드 1개를
  가진 공격자가 제한을 무한 우회하는 경로 차단).
- 제한 수치(횟수/윈도우)는 rules YAML. 카운터는 테스트에서 결정적으로
  초기화·조작 가능해야 한다(기존 redeem 계약 테스트 오염 금지) — 수단은 위임.
- 윈도우가 지난 기록은 정리된다 — IP를 바꿔가며 두드려도 메모리가
  무한정 자라지 않는다.

### B4: 대체 확인 다이얼로그 — 기존 동작 pin + 탈출구

- **무조건 확인 유지**: 타이틀에서 코드를 제출하면 진행 유무와 무관하게
  대체 확인 다이얼로그를 거친다. 진행 유무로 건너뛰지 않는다 — HttpOnly
  쿠키를 클라이언트가 읽을 수 없어 "진행 없음" 판정이 신뢰 불가이기
  때문(지난 런의 의식적 설계, 이번 런에서 재확인).
- **신규 탈출구**: 다이얼로그에 "현재 진행의 세이브 코드 받기" 경로.
  코드를 받지 못하는 모든 경우(세션 없음 401 / 밴 세션 / 서버 오류 /
  네트워크 실패)는 코드 대신 솔직한 톤의 실패 문구를 보이고, 갈아타기는
  계속 진행 가능하다 — 탈출구 실패가 redeem 을 막지 않는다. 성공하면
  코드를 화면에 보이고 클립보드 복사를 제공한다.
- 확인/취소 후 상태: 취소는 코드 입력값을 보존하고 아무 요청도 보내지
  않는다(기존 동작).
- 문구는 프론트 톤 홈 — 컴포넌트 인라인 금지. 코드 복사에 클립보드
  API를 쓰며(기존 경로 승계), 클립보드 실패가 코드 표시를 막지 않는다.
- 이 가드는 클라이언트 강제다 — 서버 계약(B3)은 무경고 redeem을
  허용한다 (Reversibility Ledger의 의식적 결정).
- 무조건 확인 + 탈출구 존재는 vitest 로 pin (Req 9).

### B5: 넛지 — 프론트 (+ localStorage)

- 최소 관측 계약:
  - `has_save_code` 가 참인 세션에는 절대 노출하지 않는다(B2b 권위 —
    진입 시점 값 + 세션 중 발급/회전 성공 반영).
  - 노출 조건은 관측 가능한 세션 상태(누적 턴 수)의 순수 함수이고,
    임계값은 튜닝 홈에 산다 — vitest 가 설정된 임계값 기준으로 경계
    양쪽을 pin 한다.
  - 한 번 닫으면 같은 기기에서 반복 노출되지 않는다.
  - 단, 이 기기에서 **코드 없는 새 세션**으로 진입하면(진입 응답이
    `status: "new"` + `has_save_code` 거짓) 다시 노출될 수 있어야 한다 —
    쿠키 소멸로 새 세션이 된 플레이어가 넛지를 영영 못 보는 상태를
    방지(코드로 복원해 들어온 세션은 코드를 보유하므로 해당 없음).
  - 저장이 불가능한 환경(프라이버시 모드)에서는 재노출될 수 있다(무해,
    기록된 한계).
  - 트리거 임계값·문구는 프론트 톤 홈에 산다 — 서버 rules YAML 값을
    브라우저로 전달하는 표면이 없으므로(패널 지적) 클라이언트 홈이
    유일하게 도달 가능한 선택. 두 곳 중복 금지.
- localStorage 는 이 런의 정식 터치포인트다: 넛지 dismiss 플래그 (기존
  재방문 힌트 패턴과 같은 저장소). 세션 신원·진행은 절대 localStorage에
  두지 않는다 — 신원은 쿠키 단일 소스 (Ledger).
- 넛지 판정 로직은 vitest 로 pin (Req 9).

### B6: 배포 env — NANPASEOM_INSECURE_COOKIE

허용목록 계약: `"1"` / `"true"` (대소문자 무시)만 "켜짐"(=Secure 생략).
빈값·`"0"`·`"false"`·오타·기타 모든 값은 "꺼짐"(=Secure 유지). falsy
목록 방식 폐지. 주의: `"yes"`/`"on"` 등 기존에 켜짐이던 값의 의미가
뒤집힌다 — 기존 배포 env 영향은 Ledger에 기록.

### B7: strike.register — 내부 계약 하드닝

전제: 존재 확인된 세션만 받는다. 위반(미지의 세션) 시 조용한 무동작
대신 즉시 실패한다 — **실제 예외로**(bare `assert` 금지: `python -O`
에서 조용한 무동작으로 되돌아가면 하드닝 자체가 사라진다). 경계 관점의
계약: 이 실패는 기존 호출부에서 **도달 불가**여야 하며(테스트로 pin),
따라서 플레이어가 `/turn` 중 500 을 보는 일은 없다. 도달 가능해지면
그것이 버그 신호다.

## Reversibility Ledger

### Decided (hard to change)

- 신원 = 쿠키 단일 소스, 무계정·무로그인 — 유지. 단, 코드 관리 부담이
  사용자 몫이라는 트레이드오프를 사람이 재확인함: 사용자 부담이 실제로
  확인되면 언젠가 계정/로그인 재검토. (from knowledge.md, ADR 0033 재확인)
- 쿠키 속성 4종 HttpOnly/Secure/SameSite=Lax/Max-Age 180일 — 유지. (from knowledge.md, ADR 0034/0037)
- 세이브 코드 형식 `WORD-XXXX`(프리픽스 단어 15개) — 유지, 회전에도 형식
  불변. (from knowledge.md, ADR 0036)
- 스택 React+Vite, bun — 유지. 프론트 테스트 러너로 vitest 도입(단방향
  선택은 아니나 설정·관습이 굳는 결정).
- **활성 코드는 세션당 정확히 1개. 회전 시 이전 코드 즉시 무효, 유예
  기간 없음.** 스키마는 `sessions.save_code` 단일 컬럼 유지(코드 히스토리
  없음). 따라서 무효화된 코드는 소각되지 않고 민팅 네임스페이스로 돌아가며
  ("영구 무효"가 아니라 "재민팅 전까지 무효"), 죽은 코드와 오타를 구분해
  안내할 수도 없다. 유예·소각·구분을 원하게 되면 스키마 변경 필요.
- **무조건 대체 확인을 유지한다(지난 런 설계 재확인).** HttpOnly 쿠키를
  클라이언트가 읽을 수 없어 "이 기기에 진행 없음" 판정이 신뢰 불가이므로,
  진행 유무로 다이얼로그를 건너뛰지 않는다. 이번 런의 델타는 탈출구
  추가뿐. (패널이 shipped code 대조로 지적, 사람이 확인)
- **갈아타기 경고의 강제 지점은 클라이언트(배포된 UI)다.** 서버 redeem
  계약은 무경고 redeem을 계속 허용한다 — 직접 API 호출은 보호 밖.
  서버측 강제(확인 토큰 등)로 옮기려면 API 계약 변경이 필요함을 알고 결정.
- **넛지 판정의 권위는 서버다 — 세션 진입 응답(bootstrap + redeem 공유
  shape)에 `has_save_code` 추가.** 클라이언트만으로는(HttpOnly 쿠키 +
  새로고침에 사라지는 메모리 상태) "코드 발급 여부"를 알 수 없어 계약이
  성립하지 않으므로, 가산적 API 필드로 해결. 응답 표면이 넓어지는 대신
  신원은 여전히 본문 밖. (패널 3인이 공통 지적 — bootstrap 단독으로는
  redeem 경로와 세션 중 발급/회전에서 값이 낡는다.)
- **넛지는 best-effort다 — "코드 보유"는 "코드를 실제로 적어뒀다"가
  아니다.** 탈출구나 발급 버튼을 눌러 코드가 민팅되면 `has_save_code`
  는 영구히 참이 되어 그 세션엔 넛지가 다시 뜨지 않는다. 실제 기록
  여부를 아는 신호는 무이력 단일 컬럼 스키마에 없으며, 더 똑똑한 넛지를
  원하면 스키마 변경이 필요함을 알고 수용.
- **넛지 임계값·문구는 프론트 톤 홈이 소유한다.** 서버 rules YAML 값을
  브라우저로 전달하는 표면이 없어 rules YAML 분기는 새 엔드포인트를
  요구하기 때문 — 소유처 위임을 철회하고 확정.
- **회전은 추가 유출 차단이지 침입자 축출이 아니다 — 의식적 수용.**
  유출된 코드를 공격자가 먼저 redeem하면 공격자도 쿠키 바인딩을 얻고,
  회전은 코드만 죽이지 기존 쿠키 바인딩은 죽이지 않는다. 공격자가 먼저
  회전하면 원 주인은 이주 수단을 잃는다. 무계정 모델에서는 주인과
  공격자를 구분할 방법이 없어 진짜 해결은 계정뿐(Out of Scope) — 패널
  `[BLOCKING]` 을 사람이 검토하고 수용 (재검토 트리거: 계정 도입 런).
- **redeem 시도 제한은 직결 IP 기준, XFF 불신뢰, 단일 프로세스 메모리.**
  리버스 프록시/Cloudflare 뒤에서는 전 사용자가 한 IP로 묶여 무의미해지고,
  멀티 워커에서는 제한이 워커 수배로 늘어난다 — 배포 런에서 재검토
  필수 항목으로 기록. 코드 공간(~1,390만 ≈ 23.7비트)은 이 제한에만
  기대고 있으며, 살아있는 코드 풀이 커질수록 추측 성공률이 오른다는 점도
  함께 수용(재검토 트리거: 플레이어 규모 증가 또는 배포 런).
- **INSECURE_COOKIE 허용목록 반전은 기존 env 값의 의미를 바꾼다** —
  `"yes"`/`"on"` 등은 이제 "꺼짐". 현재 로컬 dev 외 배포 env가 없는
  시점이라 영향 없음을 확인하고 결정.
- bearer 쿠키 서명 없음 / 무기한 보존·삭제 경로 없음 / 대량 민팅 방어
  없음 — 이번 런에서도 의식적 보류 (Out of Scope). (from knowledge.md, ADR 0034)
- 세이브 코드는 credential이다. HTTPS 전제는 배포 런에서 완성 — 그
  전까지 평문 HTTP 구간은 한시적 상태로 인지.

## Conventions

초안 시 사용):

1. 반복 리터럴은 한 집에 — 쿠키 상수는 `session_cookie.py`, 서버 튜닝
   값(레이트리밋 수치)은 rules YAML, 프론트 튜닝 값(넛지 임계값)은
   프론트 톤 홈. 코드 두 곳에 같은 숫자 금지.

   프론트 시스템 문구는 tone 홈. 이번 런의 새 문구(429, 회전 안내,
   탈출구, 넛지) 전부 포함. 톤은 "솔직한 시스템 톤" 유지. 테스트도 이
   상수를 import 해서 단언한다(한글 리터럴 인라인 금지 — 하드코딩 게이트).
   (from knowledge.md)
4. ~300줄 초과 시 분리 리뷰. App.tsx(534줄)의 분리 리뷰 결정: 이번 런
   프론트 UI 작업 선행으로 applyTurn+sendTurn 훅 추출(동작 보존)을
   실행하기로 사람이 확정 — 이 사실의 기록 홈은 이 항목 하나다
   (Requirements에 중복하지 않음). (from knowledge.md — 지난 런이 남긴 절단선)

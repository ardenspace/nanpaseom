# Manual check — 세이브 연속성 런

브라우저에서 눈으로 확인할 항목. 코드를 읽지 않고 그대로 걸을 수 있게
쓴다. 최종 수락 때 이 체크리스트를 사람이 걷는다.

띄우는 법: `docker compose up -d db` → 백엔드 `.venv/bin/uvicorn
app.api.main:app --port 8765` → 프론트 `cd frontend && bun run dev`
(5173, /api 는 8765 로 프록시). **수락 확인은 `bun run build` 로 새로
빌드한 dist 에 대해 수행할 것** (낡은 번들로 확인하는 사고 방지).

## Phase 2 — 회전과 추측 방어

- [ ] **회전 도달**: 시작 → 대화 몇 턴 → 세이브 코드 보기(발급) 패널을
      연다. 패널에 `코드 복사` / `새 코드로 바꾸기` / `닫기` 세 버튼이
      보이는가.
- [ ] **경고가 바꾸기 *전에* 나온다**: `새 코드로 바꾸기` 를 누른다.
      아직 코드가 안 바뀌어야 하고, 화면의 코드는 그대로 남은 채
      "새 코드를 발급하면 이전 코드는 더 이상 쓸 수 없습니다…" 경고가
      뜨는가. 이때 버튼은 `새 코드로 바꾸기` / `취소` 인가.
- [ ] **취소가 안전한가**: `취소` 를 누르면 원래 패널로 돌아오고 코드가
      그대로인가. (서버 호출이 없었어야 한다.)
- [ ] **회전 성공 표시**: 다시 `새 코드로 바꾸기` → 확인. 패널이 열린
      채로 **새 코드**가 보이고, 복사 버튼 라벨이 `코드 복사` 로
      리셋되는가.
- [ ] **옛 코드가 진짜 죽었는가**: 회전 전 코드를 적어뒀다가, 시크릿
      창(또는 쿠키 삭제)에서 타이틀 → `세이브 코드로 이어하기` 에 옛
      코드를 넣는다. 실패 안내가 뜨고 들어가지지 않아야 한다.
- [ ] **새 코드는 살아있는가**: 같은 창에서 새 코드를 넣으면 그 세션의
      대화가 이어지는가.
- [ ] **문구 모순 제거**: 발급 패널 설명문이 "다시 확인해도 코드는
      바뀌지 않습니다" 라고 단정하지 않는가 (회전이 있으니 거짓).
      현재 문구: "이 코드를 적어 두면 다른 기기에서 이어할 수 있습니다.
      새 코드로 바꾸기 전까지는 다시 확인해도 같은 코드가 나옵니다."
      — 읽었을 때 자연스러운가.
- [ ] **시도 제한 체감**: 시크릿 창에서 아무 코드나(예: `ZZZZ-ZZZZ`)
      11번 연속 넣는다. 10번째까지는 평소의 실패 안내, 11번째부터
      "잠시 후 다시" 류의 제한 안내로 바뀌는가. 안내가 NPC 말투가
      아니라 시스템 말투인가. **주의**: 제한은 IP당 10회/1시간이라
      한 번 걸면 그 IP 는 한 시간 잠긴다 — 나머지 항목을 먼저 걷고
      이 항목을 마지막에 하거나, 백엔드를 재시작해 리셋할 것
      (프로세스 메모리 저장이라 재시작하면 초기화).

## Phase 3 — 갈아타기 탈출구

준비: 기기 A(평소 브라우저)에서 몇 턴 플레이해 진행을 만들어 둔다.
기기 B 역할은 시크릿 창으로 대신할 수 있다.

- [ ] **경고는 여전히 무조건 뜬다**: 시크릿 창(진행 없음)에서 타이틀 →
      `세이브 코드로 이어하기` → 아무 코드나 넣고 제출. 진행이 없는
      기기인데도 대체 확인 다이얼로그가 뜨는가. (진행 유무로 건너뛰면
      회귀다 — 쿠키를 못 읽으니 '진행 없음' 판정을 믿을 수 없다는 게
      이 설계의 이유.)
- [ ] **탈출구가 보이는가**: 그 다이얼로그 안에, 경고 문구와
      `대체하고 이어하기`/`돌아가기` 버튼 *사이*에
      `현재 진행의 세이브 코드 받기` 가 있는가.
- [ ] **탈출구 성공 경로**: 진행이 있는 기기 A에서 같은 흐름을 밟고
      탈출구를 누른다. 버튼 자리에 코드가 나타나고 복사 버튼이 함께
      뜨는가. 그 코드를 적어 둔다.
- [ ] **적어 둔 코드가 진짜 돌아오는 길인가**: 이어서 다른 코드로
      갈아탄 뒤, 방금 적어 둔 코드로 다시 이어하기 해서 원래 진행이
      돌아오는가. (이게 이번 런의 핵심 — "버리기 전에 돌아올 길".)
- [ ] **탈출구 실패가 갈아타기를 막지 않는가**: 시크릿 창(세션 없음)에서
      탈출구를 누른다. "이 기기의 세이브 코드를 받지 못했습니다…" 안내가
      뜨고, 그 상태에서도 `대체하고 이어하기` 가 눌리며 실제로 갈아타지는가.
      (실패가 갈아타기를 막으면 회귀다.)
- [ ] **취소가 안전한가**: 코드를 입력하고 다이얼로그를 띄운 뒤
      `돌아가기`. 입력한 코드가 그대로 남아 있고, 아무 일도 일어나지
      않았는가.
- [ ] **문구가 사람 말인가**: 탈출구 실패 문구가 NPC 말투가 아니라
      솔직한 시스템 말투로 읽히는가. 현재 문구: "이 기기의 세이브 코드를
      받지 못했습니다. 이 기기에 남아 있는 진행이 있다면, 지금 계속할
      경우 그 진행으로 돌아올 방법이 없습니다."

## Phase 4 — 코드 뽑기 넛지

임계값은 신규 세션 기준 **6턴**(`frontend/src/tone.ts` 의
`SAVE_CODE_NUDGE_AFTER_TURNS`). 넛지 dismiss 플래그는 localStorage 에
`nanpaseom.saveCodeNudgeDismissed` — 다시 보려면 이 키를 지우거나
시크릿 창을 쓴다.

- [ ] **임계 전에는 안 뜬다**: 시크릿 창에서 새로 시작해 5턴까지
      대화한다. 입력 바 위에 넛지 배너가 없는가.
- [ ] **6턴째에 뜬다**: 한 턴 더 보낸다. 입력 바 *바로 위*에 배너가
      뜨는가. 문구가 NPC 말투가 아니라 시스템 말투로 보이는가(색/모양이
      NPC 말풍선과 확실히 구분되는가). 현재 문구: "이 브라우저의 접속
      정보가 사라지면 지금까지의 대화를 잃을 수 있습니다. 세이브 코드를
      받아 두면 다른 기기에서도 이어할 수 있습니다."
- [ ] **행동 버튼이 실제로 코드를 준다**: `세이브 코드 받기` 를 누르면
      기존 세이브 코드 패널이 열리고 코드가 나오는가.
- [ ] **코드를 받으면 넛지가 사라진다**: 패널을 닫고 대화를 몇 턴 더
      이어간다. 배너가 다시 뜨지 않는가. (새로고침 없이도 사라져야
      한다 — 서버에 다시 묻지 않고 즉시 반영하는 게 계약이다.)
- [ ] **새로고침 후에도 안 뜬다**: 코드를 받은 상태에서 새로고침해
      이어간다. 배너가 없는가. (서버가 진입 응답에 코드 보유를 실어
      주므로 기억이 아니라 사실로 판정된다.)
- [ ] **`나중에 하기` 가 유지되는가**: 다른 시크릿 창에서 6턴을 채워
      배너를 띄우고 `나중에 하기` 를 누른다. 그 뒤 몇 턴을 더 보내도
      다시 안 뜨는가. 새로고침해 이어가도 안 뜨는가.
- [ ] **쿠키가 사라지면 다시 뜬다**: 위 상태에서 쿠키만 지우고(또는
      개발자도구 Application 에서 `session_uuid` 삭제) 새로고침해 새
      세션으로 시작한다. 6턴 뒤 배너가 **다시** 뜨는가. — 이게 넛지가
      노리는 바로 그 사람(코드 없이 쿠키를 잃는 플레이어)이라, 여기서
      안 뜨면 기능이 목적을 잃는다.
- [ ] **코드로 복원한 세션엔 안 뜬다**: 세이브 코드로 이어하기로 들어온
      뒤 6턴 이상 대화한다. 배너가 안 뜨는가(그 세션은 코드를 갖고 있다).

### 절차 메모 / 눈에 띈 것

- 9번(시도 제한)을 마지막에 걸었지만, 5·8번에서 이미 redeem 예산 3회를
  썼기 때문에 "10회까지 404, 11회째 429" 를 그대로 관측하려면 예산이
  깨끗해야 했다. 그래서 9번 직전에 uvicorn 을 한 번 재시작해
  카운터를 리셋했다(프로세스 메모리 저장 — 위 Phase 2 체크리스트에
  적힌 것과 같은 성질). 재시작 뒤 세션·세이브 코드·history 는 DB 에
  있으므로 아무것도 잃지 않는다.
- 7번에서 history 가 11개가 아니라 8개인 것은 진입 응답이 최근 8개만
  싣기 때문(`load_recent_turns(limit=8)`) — 오프닝 대사가 창 밖으로
  밀려난 것이고 손실이 아니다. 화면에서 "예전 대사가 안 보인다" 로
  읽힐 수 있으니 사람 확인 때 참고. 이전 워크와 같은 관측.
- 서버는 기동 시 마이그레이션을 적용하지 않는다(`apply_migrations` 는
  테스트/수동 경로에서만 호출). 이 워크도 사전에 수동으로 적용해
  띄웠다. 로컬/배포 절차의 문제일 뿐 제품 동작은 아니다.
- **이전 세 워크(`afd8f4e`, `7d93282`, `3ea2257`) 대비 HTTP 동작 차이
  0건.** 이번 변경(백드롭 눌림 + 모션 축소)은 예상대로 HTTP 표면에
  흔적을 남기지 않았다 — 단, 서빙되는 CSS *바이트* 에는 들어 있음을
  위에서 확인했다. 누른 순간 배경이 밝아지는지, 모션을 줄인 환경에서
  호흡이 멈추는지는 브라우저에서만 보이므로 아래 Phase 6 체크리스트로
  사람이 걸어야 한다.
- 놀란 점 없음. 8번 회전의 `Set-Cookie` 부재, 3번 발급의 `Set-Cookie`
  부재, redeem 성공 시의 재바인딩 모두 코드 주석의 계약과 일치했다.

## Phase 6 — 수락 수정 (백드롭)

- [ ] **요청 중 백드롭이 화면을 죽이지 않는가**: 타이틀에서 코드를 넣어
      대체 확인 다이얼로그를 띄우고 `현재 진행의 세이브 코드 받기` 를
      누른 **직후**(응답 오기 전) 다이얼로그 바깥 어두운 영역을 클릭한다.
      다이얼로그가 그대로 남아 있고(닫히지 않고), 응답이 오면 그 안에
      결과가 표시되는가. 그 뒤 바깥을 다시 클릭하면 정상적으로 닫히고
      타이틀 버튼들이 살아 있는가.
- [ ] **다시 열었을 때 깨끗한가**: 위에서 닫은 뒤 다시 코드를 제출해
      다이얼로그를 연다. 이전에 받았던 코드나 실패 문구가 남아 있지
      않고 `현재 진행의 세이브 코드 받기` 버튼이 처음 상태로 있는가.
- [ ] **채팅 패널도 같은가**: 채팅에서 세이브 코드 패널 →
      `새 코드로 바꾸기` → 확인을 누른 **직후** 바깥을 클릭한다. 패널이
      그대로 남고, 회전이 끝난 뒤 채팅이 정상 동작하는가. (수정 전에는
      채팅 전체가 얼고 NPC 타이핑 표시가 진행 중이 아닌 턴을 진행 중인
      것처럼 보여줬다.)
- [ ] **누른 순간 배경이 답하는가**: 요청이 나가 있는 동안(응답 오기 전)
      다이얼로그 바깥 어두운 영역을 누른다. 누르고 있는 그 순간 배경이
      한 번 밝아졌다가 손을 떼면 천천히 가라앉는가. **마우스와 폰 양쪽에서
      확인한다 — 폰이 핵심이다**(커서 `progress` 도 숨쉬는 농도도 폰에는
      사실상 없는 신호라, 접촉에 답하는 건 이것뿐이다). 짧게 톡 쳐도
      눌린 게 읽히는가.
- [ ] **동작 줄이기에서도 '요청 중'이 보이는가**: OS 의 '동작 줄이기'
      (reduce motion / 손쉬운 사용 → 동작 줄이기)를 켠 뒤 같은 요청을
      건다. 배경이 오르내리며 흔들리지 않으면서도, 평소보다 짙게 서 있어
      '지금 요청 중'이라는 건 여전히 읽히는가. 이 상태에서도 위의 눌림
      반응은 그대로 살아 있는가.

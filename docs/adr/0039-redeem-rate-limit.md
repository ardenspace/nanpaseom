# ADR 0039: redeem 시도 제한 — 직결 IP 당 10회/시간, XFF 불신뢰, 프로세스 메모리

- Status: Accepted
- Date: 2026-08-21
- Deciders: Arden (수치와 트레이드오프를 검토 후 수용), Claude (세이브 코드 회전 talpi 런)

## Context

ADR 0034 재검토 목록의 "세이브 코드 무차별 대입 무방어 (레이트 리밋
아웃)"는 코드가 *스냅샷*이라면 미뤄도 될 항목이었다. 하지만 이 코드는
스냅샷이 아니라 **살아 있는 세션의 열쇠**다 — redeem 이 성공하면 그
순간 요청한 브라우저에 해당 세션이 쿠키로 바인딩된다
(`app/api/main.py` `_entry_response` 의 Set-Cookie). 즉 온라인 추측
성공 = 세션 탈취이고, 이건 "남의 저장 파일 하나를 훔쳐본다"와는 다른
위협 등급이다. ADR 0038 이 유출 *이후*의 회전 경로를 열었지만, 애초에
맞혀 들어오는 경로는 여전히 열려 있었다.

코드 공간은 15 × 31^4 ≈ 1,385만 (형식·공간의 서식지는 ADR 0036).
오프라인 대입에는 우스운 크기지만, 온라인에서는 **시간당 몇 번을
허용하느냐**가 실질 방어의 전부가 된다. 그 숫자를 고르고, 고르면서
버린 것들을 적는 게 이 ADR 이다.

## Decision

1. **직결 IP 당 10회 / 3600초 슬라이딩 윈도우.** 판정은
   `app/api/rate_limit.py` `allow(key, *, limit, window_seconds)`,
   수치의 단일 홈은 `rules/save_code.yaml` 의
   `redeem_rate_limit_attempts` / `redeem_rate_limit_window_seconds`
   (429 문구는 `redeem_rate_limited_message`). 튜닝은 코드 수정이 아니라
   YAML 수정이고, 테스트도 숫자를 인라인하지 않고
   `load_save_code_rules()` 에서 읽는다 (`SaveCodeRules`,
   `tests/api/test_redeem_rate_limit.py::test_limit_values_and_message_live_in_rules_yaml`).
   - **왜 10인가**: 9자 코드를 잘못 옮겨 적은 사람은 2~3회 안에 맞힌다.
     10 은 그 3배 여유이고, 한 시간에 세이브 코드를 10개 제출하는 정상
     플레이어는 존재하지 않는다.
   - **왜 3600초인가**: 공격자에게 허용되는 건 하루 240회다. 유효 코드가
     1,000개 살아 있다고 가정해도 한 주소에서 한 번 맞히기까지 기대
     시간이 두 달 규모다. 10분 창(같은 10회)은 사람에게는 아무 차이도
     없으면서 공격자의 하루 처리량만 약 6배로 올린다 — 그래서 기각.
2. **엔드포인트에 들어온 모든 시도를 집계한다** — 형식 위반, 404, 성공
   전부. 게이트가 `SAVE_CODE_RE.fullmatch` 형식 검증보다 **앞**에 선다
   (`redeem_save_code`). 형식 위반을 공짜로 두면 "일단 아무거나 던져
   응답 시간/코드를 관찰"하는 표면이 남고, 성공을 공짜로 두면 4항이
   깨진다.
3. **성공은 카운터를 리셋하지 않는다.** 이 절이 하중을 받는 곳이다:
   리셋하면 유효 코드 1개를 쥔 공격자가 성공 한 번으로 예산을
   갱신해 가며 무한히 추측할 수 있다 — 제한이 있으나 마나가 된다
   (회귀 pin: `test_a_success_does_not_reset_the_counter`,
   `test_successful_redeems_count_toward_the_limit`).
4. **차단된 시도는 기록하지 않는다.** `allow` 는 허용한 시도만 deque 에
   넣는다. 그래서 429 를 맞고도 계속 두드리는 쪽이 자기 윈도우를 뒤로
   밀지 못하고, 예산을 소진한 사람은 **가장 오래된 기록이 만료되는
   대로** 회복한다 (영구 롤링 잠금 아님 —
   `test_blocked_attempts_do_not_extend_the_window`,
   `test_redeem_is_usable_again_after_the_rules_window`).
5. **키는 직결 연결의 원격 주소뿐 — `X-Forwarded-For` 를 보지 않는다**
   (`client_ip`). 클라이언트가 붙여 보낼 수 있는 헤더를 믿으면 헤더 한
   줄 바꾸는 것만으로 새 예산을 살 수 있고, 그건 제한이 아니라 제한의
   흉내다 (`test_spoofed_forwarded_for_does_not_buy_a_separate_budget`).
   대가는 정직하게 적는다: **리버스 프록시/Cloudflare 뒤에서는 모든
   플레이어의 직결 주소가 프록시 하나로 붕괴한다** — 제한이 무의미해지거나,
   더 나쁘게는 한 사람의 오타가 전원을 429 로 묶는 집단 잠금이 된다.
   직결 주소를 못 읽는 호출은 공유 버킷(`UNKNOWN_CLIENT_KEY`)으로 모은다
   — 신원 불명이 우회 구멍이 되지 않게, 하나의 예산을 나눠 쓴다.
   **이 항은 배포 런의 필수 재검토 항목이다** (아래 Consequences).
6. **저장소는 프로세스 메모리** (`_hits: dict[str, deque[float]]`).
   재시작하면 초기화되고, 워커가 N개면 실효 제한이 N배가 되며, 다수 IP
   분산 공격에는 무력하다. Redis 등 공유 저장소는 개인 프로젝트 규모에서
   운영 비용이 방어 이득을 넘는다고 판단해 **Simplicity Zone 으로 수용**
   — 인프라급 방어는 배포 런의 몫이다. 시간 출처는 모듈 레벨 `now()`
   단조 시계 seam 하나로 모아 테스트가 sleep 없이 윈도우를 넘긴다
   (`tests/api/test_rate_limit_cleanup.py` 의 `FakeClock`).
7. **만료 기록은 윈도우당 1회 상각 정리한다** (`_sweep`). IP 를 계속
   바꿔가며 두드려도 남는 키는 최근 두 윈도우 안에 실제로 요청한 주소뿐이라
   메모리가 무한정 자라지 않는다. 요청당 비용은 O(1) 에 수렴.
   관측점은 `tracked_key_count()`,
   pin 은 `test_long_running_hammering_does_not_grow_without_bound`.
8. **차단 응답은 아무것도 재바인딩하지 않는다.** 429 는 Set-Cookie 를
   싣지 않고, 문구는 "왜 막혔는지"(추측 방어)만 말하고 **입력한 코드가
   맞았는지 틀렸는지는 말하지 않는다** — 429 자체가 유효 코드 판별기가
   되면 안 된다.

## Alternatives Considered

- A. ★ chosen — 직결 IP 당 10회/3600초, 모든 시도 집계, 프로세스 메모리.
- B. 10분 창 (같은 10회) — 기각. 사람은 차이를 느끼지 못하는데 공격자의
  하루 처리량만 240 → 1,440 회로 뛴다 (1항).
- C. 성공 시 카운터 리셋 — 기각. 유효 코드 1개로 제한 전체를 무한 우회할
  수 있게 되어 3항의 하중을 그대로 무너뜨린다.
- D. 차단된 시도도 기록 (롤링 처벌) — 기각. 두드리기를 멈추지 않는 쪽에는
  차이가 없고, 오타로 예산을 태운 실제 플레이어만 영구 잠금에 가까워진다.
- E. `X-Forwarded-For` 의 첫 주소를 키로 — 기각. 신뢰 경계가 없는 상태에서
  헤더를 믿는 것은 무제한과 같다. 프록시가 실제로 앞에 서는 순간
  "신뢰하는 프록시 목록"과 함께 도입할 결정이지, 미리 열어 둘 문이 아니다.
- F. 세션/코드 단위 제한 (IP 대신) — 기각. redeem 은 세션이 성립하기
  *전에* 부르는 표면이고, 코드 단위 제한은 "이 코드가 존재한다"를 아는
  것을 전제로 해서 미지 코드 추측을 전혀 막지 못한다.
- G. 공유 저장소(Redis 등) 기반 분산 카운터 — 기각(현 시점). 6항 — 개인
  프로젝트 단일 프로세스 규모에서 과잉. 배포 형태가 정해지는 런에서
  프록시 층 제한과 함께 재검토.

## Consequences

- **재검토 트리거 1: 배포 런.** 5항(프록시 뒤 IP 붕괴)과 6항(단일 프로세스
  메모리)은 배포 형태가 정해지는 순간 **반드시** 다시 본다. 프록시가 앞에
  선다면 선택지는 둘 — 신뢰 프록시 목록 + `X-Forwarded-For` 파싱, 또는
  제한 자체를 프록시/Cloudflare 층으로 올리기. 워커를 여러 개 띄운다면
  공유 카운터가 같이 필요해진다. 재검토 목록의 단일 서식지는 여전히
  ADR 0034 이고, 이 항목의 등재는 별도 스텝이 처리한다.
- **재검토 트리거 2: 플레이어 수 증가.** 방어가 지금 이 제한 하나에 기대고
  있고, 그 아래의 엔트로피는 ~1,385만(≈ 2^23.8)로 자격증명 기준으로는 큰
  값이 아니다 (ADR 0036 의 의식적 트레이드오프). 게다가 **살아 있는 코드
  풀은 플레이어 수와 함께 자라서 추측 1회당 적중 확률을 함께 올린다** —
  1항의 "두 달" 계산은 유효 코드 1,000개 가정에 매인 숫자다. 플레이어
  기반이 커지면 코드 길이/공간 자체를 다시 계산한다.
- ADR 0034 재검토 목록의 "무차별 대입 무방어" 항목은 **해소가 아니라
  조건부 완화**로 상태가 바뀐다: 단일 프로세스 + 직결 IP 라는 전제
  안에서만 성립한다.
- 제한이 걸린 표면은 `POST /save-code/redeem` 하나다. 발급/회전
  (`POST /save-code`, `POST /save-code/rotate`)은 이미 세션 쿠키를
  요구하므로 추측 대상이 아니다.
- 카운터가 프로세스 전역이라 테스트 간 오염이 실재하는 위험이다 —
  `reset()` 을 경계에서 부르는 것이 스위트의 계약
  (`tests/api/conftest.py` 의 공유 `client` fixture + `fresh_limiter`).
- NAT/공용 와이파이 뒤의 여러 플레이어는 이미 지금도 한 예산을 나눠 쓴다.
  시간당 10회면 실사용에서 부딪힐 일이 사실상 없다고 보고 수용.

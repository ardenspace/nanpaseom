# ADR 0038: 세이브 코드 회전 — 세션당 활성 코드 1개, 무유예, 소각 없음

- Status: Accepted
- Date: 2026-08-21
- Deciders: Arden (패널 `[BLOCKING]` 지적을 검토 후 수용), Claude (세이브 코드 회전 talpi 런)

## Context

ADR 0034 의 재검토 목록에는 "세이브 코드 … 유출 시 무효화/회전 경로 없음
(idempotent 영구 자격증명)"이 올라 있었다. 발급(`POST /save-code`)은
의도적으로 idempotent 라서, 한 번 종이에 적힌 코드는 세션이 사는 한 영원히
그 세션의 열쇠다 — 옆에서 화면을 봤거나, 스트리밍 중 코드가 비쳤거나,
적어 둔 쪽지를 잃어버린 플레이어에게 줄 수 있는 답이 "없다" 뿐이었다.

이번 런은 그 절반 — **플레이어가 스스로 코드를 갈아끼우는 경로** — 을
`POST /save-code/rotate` 로 연다. 계정이 없는 신원 모델(ADR 0033)에서
회전이 실제로 무엇을 지켜 주고 무엇은 못 지키는지, 그 경계를 기록하는 것이
이 ADR 의 목적이다.

## Decision

1. **세션당 활성 코드 정확히 1개.** 스키마는 `sessions.save_code` 한 칸
   (nullable + UNIQUE 인덱스, `migrations/003_save_code.sql`) 그대로 —
   코드 이력 테이블을 두지 않는다. 회전은 그 한 칸의 덮어쓰기다
   (`app/api/main.py` `rotate_save_code` → `_mint` → `mint_save_code`).
   이력이 없다는 선택이 아래 3·4항을 파생시킨다.
2. **회전 시 이전 코드 즉시 무효, 유예 없음.** 응답이 나간 순간 옛 코드는
   어느 세션에도 매이지 않아 redeem 404 다. 두 코드가 동시에 유효한 순간이
   **없다**는 것이 계약 (`tests/api/test_save_code_rotate.py`
   `test_old_and_new_code_are_never_valid_at_the_same_time`). 유예 창은
   "유출 대응"이라는 회전의 유일한 존재 이유를 그 창 길이만큼 무력화한다.
   강제 장치: 민팅에 `avoid=<현재 코드>` 를 넘겨(`mint_save_code(conn,
   session_uuid, *, avoid=None)`), 무작위 재생성이 우연히 같은 문자열을
   내는 경우에도 "옛 코드가 살아남는" 결과가 되지 않게 한다.
3. **무효화된 코드는 소각되지 않는다.** 퇴역한 문자열은 민팅 네임스페이스로
   되돌아가고, 훗날 *다른* 세션의 코드로 배정될 수 있다 (확률적으로 희박 —
   공간은 15 × 31^4 ≈ 1,385만, ADR 0036). 따라서 "영구 무효"는 부정확하고
   정확히는 **"재민팅 전까지 무효"** 다. 소각 목록은 1항이 배제한 코드 이력
   스키마를 요구한다.
4. **죽은 코드와 오타를 구분해 안내하지 않는다.** 회전으로 버려진 코드는
   오타·미지의 코드와 **같은 404 문구**를 받는다 (`_redeem_not_found`,
   문구는 `rules/save_code.yaml`). 구분하려면 "이 문자열이 한때 존재했다"를
   알아야 하고, 그건 다시 코드 이력이다. 부수적으로, 구분 응답은 무차별
   대입자에게 "여긴 뭔가 있었다"는 신호를 주는 표면이기도 하다.
5. **회전은 추가 유출 차단이지 침입자 축출이 아니다.** 유출된 코드를
   공격자가 주인보다 **먼저** redeem 하면, 그 순간 공격자 브라우저에 해당
   세션이 쿠키로 바인딩된다(`_entry_response` 의 Set-Cookie). 회전은 코드를
   죽일 뿐 **이미 성립한 쿠키 바인딩은 끊지 않는다** — 공격자는 접근을
   유지한다. 반대로 공격자가 먼저 회전하면 정당한 주인이 기기 이동 경로를
   잃는다. 계정이 없는 모델에서 서버는 둘을 구분할 수단이 없다. 세션 전체를
   무효화하는 "모든 기기에서 로그아웃"은 계정 도입 없이는 성립하지 않으므로
   범위 밖으로 두고, 이 한계를 **의식적으로 수용**한다.
6. **발급과 회전을 나눈다.** `POST /save-code` 는 계속 idempotent —
   이미 적어 둔 코드를 다시 확인해도 같은 코드가 나온다. 버튼을 두 번
   눌렀다고 종이에 적은 코드가 죽는 일은 절대 없어야 한다. 회전은 "다른 걸로
   바꿔 달라"는 명시적 행동이므로 별도 URL 이다. 하나로 합치면 모든 재확인이
   조용히 플레이어의 쪽지를 무효화한다 (회귀 pin:
   `test_issue_stays_idempotent_across_a_rotation`).
7. **프론트는 confirm-first.** 회전 컨트롤은 경고
   (`SAVE_CODE_ROTATE_WARNING`)를 띄우고 두 번째 누름을 받은 뒤에야 서버를
   부른다 — 옛 코드를 쥔 누구에게도 되돌릴 수 없는 행동이기 때문. 회전 도입
   전 문구 "다시 확인해도 코드는 바뀌지 않습니다"는 이제 **거짓**이므로
   폐기하고, 같은 코드가 유지되는 *조건*을 밝히는 문구로 교체했다
   (`frontend/src/tone.ts` — 폐기된 주장은 `RETIRED_IMMUTABLE_CODE_CLAIM`
   상수로 부재를 pin).
8. **다른 기기/탭의 스테일 표시를 감수한다.** 회전 전에 다른 탭/기기에 떠
   있던 코드는 그대로 떠 있는다. 서버 계약(활성 코드 1개)은 깨지지 않고
   화면만 낡은 것이며, 이를 고치려면 크로스탭 동기화가 필요하다 — 감수.

## Alternatives Considered

- A. ★ chosen — 단일 칸 덮어쓰기 + 무유예 + 소각 없음.
- B. 유예 창 (옛 코드 N분/N시간 병존) — 기각. "옛 코드가 유출됐다"가 회전의
   전제인데 그 창 동안 유출된 코드가 계속 통한다. 이력 컬럼(옛 코드 +
   만료시각)도 요구 — 이득 없이 스키마와 상태만 늘어난다.
- C. 소각 목록 (퇴역 코드 영구 배제) — 기각. 코드 이력 테이블 + 민팅 시
   매번 조회가 필요하고, 얻는 건 1,385만 분의 1 재배정 회피뿐. 게다가
   목록은 무한히 자란다.
- D. 회전 시 세션 UUID 까지 갈아끼우기 (= 침입자 축출) — 기각. 회전을
   요청한 쪽이 주인이라는 보장이 없어(5항) 공격자에게 오히려 주인 축출
   버튼을 쥐어 준다. 축출의 전제는 "누가 주인인지 아는 것" = 계정이다.
- E. 발급 엔드포인트를 회전으로 바꾸기 (매 호출 새 코드) — 기각. 6항 —
   코드를 다시 확인하는 흔한 동작이 종이에 적힌 코드를 죽인다.

## Consequences

- ADR 0034 재검토 목록의 해당 항목은 **절반만 해소**된다: "회전 경로 없음"은
   사라졌지만 "유출 시 (이미 들어온 자를) 무효화할 경로 없음"은 5항으로
   존속한다. 목록의 서식지는 여전히 ADR 0034 다.
- **재검토 트리거: 계정 도입 런.** 5항의 한계는 계정(주인 판별 수단)이
   생기는 시점에 전면 재검토한다 — 그때 세션 단위 무효화("모든 기기에서
   로그아웃")와 코드 이력의 필요성이 같이 결정된다.
- 밴 세션은 회전하지 않는다 (401/banned 분기는 발급과 같은 결 —
   `_no_session_response` / `_banned_response`). 밴 세션의 코드는 그대로
   둔다.
- 민팅 소진(`SAVE_CODE_MINT_ATTEMPTS` 회 내 유일 코드 실패 →
   `SaveCodeMintError`)은 회전에서도 발급과 같은 어댑터(`_mint`)로 500 이
   된다 — 실질적으로 발생 불가한 안전장치.
- 플레이어에게 하는 약속이 "이 코드는 안 바뀝니다"에서 "당신이 바꾸기
   전까지 안 바뀝니다"로 이동했다. 회전 후 옛 코드를 입력하는 플레이어는
   "그런 코드 없음"만 듣게 된다 (4항의 대가).

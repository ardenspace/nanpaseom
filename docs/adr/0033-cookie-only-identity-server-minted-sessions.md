# ADR 0033: 쿠키 단일 신원 + 세션 UUID 서버 전용 민팅

- Status: Accepted
- Date: 2026-08-20
- Deciders: Arden, Claude (공개 배포 준비 talpi 런 — 패널 지적을 사람이 검토 후 결정)

## Context

공개 배포 준비 점검에서 신원 모델의 구멍 두 개가 드러났다 (knowledge.md
오픈 질문 + 리뷰 패널 지적):

1. **신원 소스 불일치**: `POST /turn` 은 요청 *본문*의 `session_uuid` 로
   신원을 받고, `POST /save-code` 는 쿠키로 받았다. 본문 신원은 아무나
   임의 UUID를 실어 보낼 수 있는 표면 — "남의 세션이 보이는 것"이 절대
   금지인 제품에서 성립 불가.
2. **클라이언트 지정 UUID 채택**: bootstrap 이 서버가 모르는(스테일)
   쿠키 UUID를 그대로 세션 행으로 채택했고, `/save-code` 는 미지 쿠키에
   대해 빈 세션을 민팅한 뒤 코드를 발급했다. 클라이언트가 고른 값이
   서버 신원이 되는 구조.

이 게임의 신원 모델은 계정/로그인 없는 익명 세션 UUID 하나가 전부라서
(기기 이동은 세이브 코드), 이 UUID의 소유 경계가 곧 개인정보(대화
텍스트) 경계다.

## Decision

1. **쿠키 단일 신원**: `/turn`·`/save-code` 의 신원은 HttpOnly 쿠키
   `session_uuid` 만. 본문 신원은 폐지 — API 파괴적 변경이지만 프론트가
   같은 레포라 동시 수정으로 흡수. 본문에 세션 번호류가 와도 **무시**
   (거부 아님 — 나중에 reject로 조이는 건 파괴적 변경이 되는 관용
   락인임을 알고 선택).
2. **서버 전용 민팅**: 세션 UUID는 서버만 생성. 서버가 모르는 UUID가
   쿠키로 와도 그 값이 세션 행이 되는 일은 없다 — bootstrap 은 미지
   값을 버리고 새 UUID를 민팅, `/save-code` 는 미지 쿠키에 401 (세션
   생성 없음).
3. **세션 생성 문은 `POST /session/bootstrap` 유일**. 쿠키 인증
   엔드포인트의 신원 판정(파싱 → UUID 검증 → 세션 존재 확인)은 단일
   공유 지점을 통과하며, 이 지점은 절대 세션을 만들지 않는다.
4. **응답 본문에서 `session_uuid` 제거**: 프론트 JS가 더 이상 쓰지
   않으므로, 자격증명이 JS 가시 영역에 남지 않는 것이 계약 — HttpOnly
   방어선을 응답 본문이 무의미화하지 않도록 (패널 재검증 지적의 해소).
5. 401 문구는 `rules/identity.yaml` (서버 발신 메시지 하드코딩 금지
   룰의 기존 패턴, ADR 0035 참조).

## Alternatives Considered

- A. ★ chosen — 쿠키 단일 소스 + 서버 민팅.
- B. 본문 + 쿠키 대조 (둘 다 받고 일치 검증) — 기각. 신원 표면이 두
  배로 남고 대조 로직 자체가 새 버그 표면. 프론트를 같이 고칠 수 있는
  상황에서 본문 신원을 존속시킬 이유가 없다.
- C. 서명 토큰 (서명/만료/회전 가능한 세션 토큰) — 기각. 익명 개인
  프로젝트 규모에 키 관리/회전 인프라가 과잉. 쿠키 값은 서명 없는
  bearer UUID로 의식적 수용 (ADR 0034 — 커뮤 공개 전 재검토 딱지).

## Consequences

- "요청 본문에 어떤 세션 번호를 실어 보내도 남의 섬이 열리지 않음"이
  계약 테스트로 박제됨 (무시 계약 + 401 계약 + B7 단일 지점 테스트).
- 서버 DB 유실 시 기존 쿠키는 미지 세션 → bootstrap 이 묻지 않고 새
  번호로 덮는다 (조용한 덮어쓰기 — 의식적 수용, ADR 0034 재검토 목록).
  진짜 복구 열쇠는 세이브 코드.
- 프론트는 401을 recoverable로 처리 — 자동 재bootstrap 1회 후 이어감.

# ADR 0040: `has_save_code` 진입 필드 + 넛지 best-effort — 코드 보유 ≠ 실제 기록

- Status: Accepted
- Date: 2026-08-21
- Deciders: Arden (패널 `[BLOCKING]` 지적을 검토 후 수용), Claude (세이브 코드 회전 talpi 런)

## Context

이번 런은 "쿠키가 사라지기 전에 코드를 쥐게 하는" 넛지를 도입했다. 그
넛지에는 타협 불가한 규칙이 하나 있다 — **이미 코드를 가진 세션은 절대
넛지 대상이 아니다**. 받아 둔 사람에게 "받아 두라"를 반복하는 안내는
잔소리이고, 시스템 목소리로 하는 모든 말의 신뢰를 같이 깎는다.

문제는 클라이언트가 그 판정을 **혼자 할 수 없다**는 것이었다. 세션
쿠키는 HttpOnly 라 JS 가 읽지 못하고(ADR 0033/0034), 프론트가 메모리에
들고 있는 `saveCode` 는 새로고침 한 번에 사라진다. 코드로 복원된 세션은
더 나쁘다 — 코드를 *입력해서* 들어왔는데도 클라이언트에는 보유 흔적이
남지 않는다. "이 세션이 코드를 갖고 있는가"를 아는 곳은 서버뿐이다.

독립 리뷰어 3인 패널이 spec 시점에 이것을 `[BLOCKING]` 으로 올렸고,
해소는 가산적 API 필드 `has_save_code` 였다 (사람이 검토 후 수용). 이
ADR 은 그 필드의 모양과 서식지, 그리고 그 필드 위에 세운 넛지가 무엇을
약속하고 **무엇은 약속하지 않는지**를 같이 못 박는다.

## Decision

1. **판정 권한은 서버 필드 `has_save_code` 다.** 진입 응답이 그 시점의
   진실을 싣는다 (`app/api/main.py` `_entry_response`). 클라이언트 단독
   휴리스틱은 절대 규칙을 확률로 바꾸는 것이라 후보가 아니었다 (Context).
2. **필드는 진입 wire shape *전체* 에 실린다.** `POST /session/bootstrap`
   과 `POST /save-code/redeem` 는 같은 성공 shape 를 공유하므로
   (`frontend/src/protocol.ts` 의 `RedeemData = BootstrapData` 별칭이 그
   의도를 기록), 삽입 지점을 `_entry_response` 하나로 두어 두 문에 같이
   실린다. 초안은 bootstrap 에만 실었는데, 그러면 **하필 redeem 경로에서
   값이 비어** 코드를 방금 입력해 들어온 사람이 넛지 대상이 된다 —
   절대 규칙이 정확히 뒤집히는 지점이었다.
   - **banned / 503 은 이 문을 지나지 않는다.** 밴 세션은 넛지 대상이
     아니고, 503 은 보고할 세션 상태가 없다. 계약도 그 둘을 요구하지
     않는다 (`tests/api/test_has_save_code.py` 의 "미pin (의도적)").
3. **값을 저장하지 않고 읽기 시점에 파생한다** —
   `repo.get_save_code(conn, session_uuid) is not None`. 새 컬럼도,
   마이그레이션도 없다: ADR 0038 이 락인한 `sessions.save_code` 한 칸이
   그대로 유일한 소스다. 파생 상태는 소스와 **어긋날 수 없다** — 불리언
   컬럼을 따로 두면 발급·회전·redeem 세 경로가 전부 그것을 갱신해야 하고,
   한 곳만 빠뜨리면 "코드가 있는데 넛지가 뜨는" 조용한 거짓이 된다.
4. **세션 도중의 발급·회전 성공은 클라이언트가 즉시 참으로 간주한다.**
   두 응답이 이미 코드를 돌려주므로 확인용 왕복이 필요 없다
   (`App.tsx` `issueSaveCode` / `rotateSaveCode` 의 `setHasSaveCode(true)`).
   계약은 "그 시나리오에서 `/session/bootstrap` 호출은 정확히 1회"로
   pin 되어 있다 (`frontend/src/App.saveCodeNudge.test.tsx`).
5. **`/turn` 401 복구만은 서버 권한을 그대로 존중한다.** 이 경로는
   클라이언트가 플레이 도중 다른 세션으로 갈아타는 유일한 지점이라,
   복구 응답의 `has_save_code` 를 버리면 **다른 탭이 코드를 가진 세션으로
   쿠키를 재바인딩한 경우** 절대 규칙이 실제로 깨진다. 검증이 이 누락을
   잡아 `useTurn.ts` 가 `onEntrySaveCode(b.data.has_save_code === true)`
   로 고쳐졌다 — 화면(히스토리)은 유지하는 resumed 분기에서도 이 값만은
   서버가 권한이다.
6. **넛지는 best-effort 다 — "코드 보유"는 "코드를 실제로 적어 뒀다"가
   아니다.** 발급 버튼(또는 대체 확인 다이얼로그의 탈출구)을 누르면 코드가
   민팅되고 플래그는 영구히 참이 된다. 화면에 뜬 코드를 그냥 닫아버린
   플레이어도 그 세션에서는 넛지를 다시 보지 못한다. ADR 0038 의 단일 칸
   무이력 스키마에는 "적어 뒀다"는 신호 자체가 없고, 더 똑똑한 넛지는
   스키마 변경을 요구한다 — **알고 수용한다**.
7. **재노출 규칙: 코드 없는 `new` 진입에서만 dismiss 플래그를 푼다**
   (`App.tsx` `enterNudgeSession`). resumed 에서는 풀지 않는다(닫은 결정이
   아직 유효하다). redeem 성공에서도 풀 일이 없다 — 코드로 복원된 세션은
   `has_save_code` 가 참이라 애초에 이 분기에 오지 않는다. 이 해제가
   지키는 사람은 정확히 **코드 한 번 안 받은 채 쿠키를 잃은 플레이어**다.
   해제가 없으면 그는 그 기기에서 넛지를 영영 다시 보지 못한다.
8. **resumed + 코드 없음은 즉시 노출 자격.** 40턴을 쌓아 두고 코드가
   없는 재방문자가 이 넛지의 과녁 한복판인데, 그에게 다시 N턴을 기다리게
   하면 과녁을 빗나간다. 구현은 그런 진입에서 세션 턴 카운터를 임계값으로
   시드하는 것(`setTurnCount(isNew ? 0 : SAVE_CODE_NUDGE_AFTER_TURNS)`).
   복원된 히스토리에서 턴을 *세는* 방식은 기각했다 — `_resumed_payload`
   가 `limit=8` 로 잘라 오므로 거기서 얻은 수는 **지어낸 숫자**다.
9. **dismiss 플래그는 localStorage, 기기당** (`saveCodeNudge.ts` +
   `localFlag.ts`). 이번 런의 유일한 새 저장소 접점이며, **신원과 진행은
   여기 절대 오지 않는다** — 신원은 쿠키 단일 소스(ADR 0033). 프라이버시
   모드 등 저장소 접근이 throw 하는 환경에서는 던지지 않고 "닫은 적 없음"
   으로 강등한다: 최악의 결과가 무해한 재노출뿐이기 때문.
10. **임계값과 문구는 프론트 톤 홈(`frontend/src/tone.ts`)에 산다, rules
    YAML 이 아니라.** rules YAML 은 서버 것이고 **그 값을 브라우저로 나르는
    전송 경로가 없다** — 지금 도달 가능한 단일 홈은 클라이언트 쪽뿐이다.
    신규 세션 임계값은 `SAVE_CODE_NUDGE_AFTER_TURNS = 6`, 판정은
    `shouldShowSaveCodeNudge` 순수 함수가 소유한다 (숫자 인라인 금지).
11. **넛지에 행동 버튼을 단다** (`SAVE_CODE_NUDGE_ACTION`). "코드를 받아
    두라"고 말하면서 받는 방법을 주지 않으면 플레이어가 헤더 버튼을 찾아
    헤맨다. 버튼은 **기존 발급 패널을 그대로 연다** — 코드가 보이는 표면을
    둘로 늘리지 않는다.

## Alternatives Considered

- A. ★ chosen — 진입 응답의 파생 불리언 + 기기 로컬 dismiss + best-effort 수용.
- B. 클라이언트 단독 판정 (메모리 `saveCode` / 로컬 "코드 있음" 플래그) —
  기각. 메모리는 새로고침에 사라지고, 로컬 플래그는 기기-로컬 추측이라
  코드로 복원된 세션·다른 기기에서 그냥 틀린다. 절대 규칙을 지킬 수 없는
  수단으로 절대 규칙을 지키는 시늉이 된다.
- C. bootstrap 에만 필드 추가 — 기각. 2항 — 값이 비는 곳이 하필 redeem,
  즉 코드 보유가 가장 확실한 경로다.
- D. 별도 조회 엔드포인트 (`GET /save-code/status` 류) — 기각. 진입 응답에
  실으면 추가 왕복 0, 새 공개 표면 0 이다. 표면을 늘리는 건 그 자체로
  위생 비용(ADR 0035).
- E. `sessions` 에 불리언 컬럼 신설 — 기각. 3항 — 같은 사실의 두 번째
  서식지는 곧 drift 다. 게다가 마이그레이션 비용을 내고 얻는 게 없다.
- F. dismiss 플래그를 서버 세션에 저장 — 기각. 스키마와 쓰기 경로가 늘고,
  넛지는 순수 UI 상태다. 무엇보다 이 플래그가 지켜야 할 대상(쿠키를 잃은
  플레이어)에게는 서버 세션 자체가 이미 사라져 있다.
- G. 임계값을 `rules/*.yaml` 로 — 기각(현 시점). 10항 — 값을 나르려면
  엔드포인트를 새로 열어야 하고, 그러면 튜닝 값의 홈이 둘이 된다.
- H. "실제로 적었는가"를 추적 (복사 클릭 / 확인 체크박스 등) — 기각.
  단일 칸 무이력 스키마에 그 신호가 없고, 복사 클릭조차 "적었다"의 증거가
  아니다 (복사해 놓고 잃어버리는 것이 정확히 이 넛지가 다루는 사고다).
  6항으로 한계를 수용하는 쪽을 택했다.

## Consequences

- 넛지가 놓치는 플레이어의 모양이 정확히 정해졌다: **코드를 화면에 띄웠지만
  적지 않은 사람.** 그 세션은 다시 안내받지 못한다. 이건 버그가 아니라
  6항의 대가다.
- 대체 확인 다이얼로그의 탈출구(`rescueSaveCode`)도 서버에 코드를 민팅하므로
  **다음 진입부터** `has_save_code` 가 참이다. 클라이언트가 왕복 없이 즉시
  참으로 올리는 경로는 4항의 발급·회전 둘뿐 — 탈출구는 그 다이얼로그 안에만
  결과를 남기므로 채팅 화면의 넛지 상태를 그 자리에서 만지지 않는다.
- **재검토 트리거: "실제 기록" 신호가 필요해지는 순간.** 그건 코드 발급
  이력(ADR 0038 이 의식적으로 배제한 스키마)을 요구하고, 그 스키마가 생기는
  런에서 넛지 규칙 전체를 다시 본다.
- 계약이 banned/503 에 대해 침묵하므로, 훗날 그 응답에 필드를 싣기로 해도
  계약 위반이 아니다 — 지금 구현이 싣지 않을 뿐이다.
- localStorage 는 기기·프로필 단위라 같은 사람이 시크릿 창/다른 프로필로
  들어오면 넛지를 각각 한 번씩 본다. 무해한 재노출로 수용.
- 임계값 6 이 프론트 상수라 튜닝이 프론트 빌드를 요구한다 — "밸런스는 YAML
  수정"이라는 이 레포의 결과 다른 결이지만, 10항의 전송 경로 부재가 그
  선택을 강제한다. 서버가 클라이언트 설정을 내려 주는 경로가 생기면 같이
  재검토할 항목.
- `has_save_code` 는 가산적 변경이라 기존 필드(status/npc_id/reply/choices/
  history)는 그대로이고, 진입 응답에 세션 식별자가 없다는 계약도 그대로다
  (ADR 0033 4항).

> **상위 합의**: handoff-2026-05-14-phase-0-close.md 의 Phase 1.0 항목 = 5개 (빌더 / FastAPI / Postgres / 수리공 e2e / schema 검증 / enforcement 활성화). 본 spec 은 그 중 **Sub-1 = offline 빌더 + schema 검증** 만 범위. Sub-2 (수리공 e2e + infra + safety) 는 Sub-1 종료 후 자체 brainstorming → spec → plan cycle.

## Problem Statement

Phase 0 의 손-합성 검증 Round 2 가 `npcs/<name>.yaml` + `rules/*.yaml` 만으로 system prompt 합성 가능 (gap 0) 를 증명함. 그러나 그 합성은 *사람 손*. Phase 1.0 의 첫 단계 = **그 합성을 결정성 있는 함수로 코드화** — yaml 의 *지시* 가 LLM 의 *입력* 으로 자동 변환되는 파이프라인.

이 단계가 빠지면 NPC 대사 / 톤 / 깨어남 가이드 가 코드에 하드코딩 되는 패턴 으로 회귀 — Phase 0 의 spec-driven workflow 학습 목표 전체가 무력화됨. 따라서 **빌더 = spec-driven 의 첫 자동화 layer**, 코드/yaml 사이 권한 경계 의 실행 형태.

또한 Phase 0 의 hand-synth 가 *1 cell (혜안 awareness 70)* 만 검증 — 빌더 의 production 범위 (4 NPC × 4 band + Layer 3 메타-디펜스 + hooks 변수) 가 그 cell 의 *상위 집합*. Sub-1 안에서 schema 의 *나머지* 영역 도 hand-synth 로 보강.

## What Makes This Cool

- **빌더 = pure function** (yaml + state → string). infra / db / network 의존성 없음. 1 일 안에 검증 가능, 학습 사이클 짧음.
- **Snapshot test 의 oracle 자체가 *사람이 먼저* 작성한 손-합성**. spec-driven 의 "결정성 빌더" 원칙이 테스트 구조 에까지 박혀있음.
- **3-layer 분리 (schema / render / test) 가 곧 spec-driven 3원칙 의 코드화** — closed vocab = schema, 지시 vs 결과 = render, verbatim = test invariant.
- **Sub-1 산출물이 그대로 Sub-2 의 의존성** — 빌더 가 안정 안되면 Sub-2 시작 안 함. fail-fast 가 phase 단위에까지 확장.

## Constraints

기존 `mechanic-spec.md`, `world-spec.md`, `mapping-spec.md` + 21 ADR 모두 상속. 본 spec 이 추가 부과:

- **언어/스택 락**: Python 3.11+ / Jinja2 / pyyaml / pydantic v2 / pytest. (handoff line 67 의 추정 확정.)
- **출력 = system prompt string 하나**. conversation history / running memory summary / 현재 player input 은 Sub-2 (caller orchestration) 책임. system 메시지 와 user 메시지 의 자연 경계.
- **Layer 3 메타-디펜스 는 Sub-1 안**. instruction 자체가 system prompt 안에 박히는 정적 텍스트. Layer 1/2/4 는 Sub-2.
- **Determinism**: 같은 입력 → 정확히 같은 출력. snapshot test 의 전제.
- **Fail-fast**: yaml 누락/타입 mismatch/enum 위반 → boot 단계 throw. silent default 또는 fallback X.

## 권한 경계 (이 spec 내)

- **이 spec** = Sub-1 의 *디자인 의도 + 결정 lock + scope*. 구현 detail / 함수 signature 의 *최종 모양* 은 plan 단계.
- **ADR 0022 / 0023 / 0024** = 이 spec 안에서 결정된 3개 spec-level 결정 의 audit trail.
- **`rules/prompt_skeleton.yaml`** (신설) = Jinja template + Layer 3 메타-디펜스 instruction 의 source of truth. NPC 무관.
- **`npcs/*.yaml`** (기존 + 신설 필드) = NPC operational data 의 source of truth.

## Decisions Locked (이 brainstorming 산물)

### Decision 1 — `awakening_guidelines.*.examples` rename → `player_input_examples` (→ ADR 0022)

**Context**: surigong.yaml 등 4 NPC yaml 의 `awakening_guidelines.high_impact.examples` 등 필드 가 "player 입력 예시" 인데 필드명 `examples` 는 모호 — Round 1 손-합성 에서 NPC 대사 로 오해됨.

**Decision**: 4 NPC yaml × 4 sub-section (`high_impact` / `medium_impact` / `low_impact` / `decrease`) = 16 자리 의 `examples` 키 → `player_input_examples`. ADR 0021 의 `player_choice_tones` / `npc_tone` 대칭 rename 패턴 과 동일.

**Rejected**: 빌더 코드 가 라벨 변환 (yaml 키 유지, 빌더 가 `Player input examples:` 라벨 붙임) — spec-driven 의 verbatim 원칙 ("빌더 가 yaml string 을 paraphrase X") 위반.

### Decision 2 — 빌더 가 `sample_lines` + `npc_tone` 둘 다 주입, "anchor only" instruction 동봉 (→ ADR 0023)

**Context**: handoff line 98 의 미결정 — awareness 70 시점 빌더 가 시스템 프롬프트 에 무엇 박나? Round 2 손-합성 은 `npc_tone` 만 박았으나, `sample_lines` 도 NPC yaml 의 operational data — 빌더 가 무시하면 yaml 정의 가 죽음.

**Decision**: 현 band 의 `sample_lines` + `npc_tone` 둘 다 system prompt 에 박힘. 동봉 instruction = "이 lines 는 NPC 보이스 의 anchor. verbatim 복사 금지 — 톤 calibration 용." snapshot test + property test 가 verbatim 복사 회귀 검증.

**Rejected**:
- `npc_tone` 만 박기 — yaml operational data 무시.
- config flag 로 두고 empirical 결정 — spec 모호함 을 코드 if-then 으로 떠넘김, spec-driven 위반.

### Decision 3 — `identity.system_prompt_persona_intro` yaml 필드 신설 + `rules/prompt_skeleton.yaml` 신설 (→ ADR 0024)

**Context**: Round 2 손-합성 의 [페르소나] section 은 yaml 어디 에도 없는 prose — 사람이 `current_display_name` + `name_status` + `state_a.description` + `backstory_summary` + 메타-게임 instruction 을 조립. 빌더 가 deterministic 으로 재생산 하려면 *기계 가독 source* 필요. 또한 그 prose 안에 NPC-specific characterization 과 모든 NPC 공통 메타-게임 instruction 이 섞여있음.

**Decision**: 두 종류 분리.
- NPC-specific prose → `npcs/<name>.yaml` 의 `identity.system_prompt_persona_intro` 필드 신설 (verbatim string, 3-5 문장, 디자이너 authoring).
- 메타-게임 instruction + Layer 3 메타-디펜스 + 시스템 프롬프트 sections order → `rules/prompt_skeleton.yaml` (Jinja template, 모든 NPC 공통).
- 빌더 = skeleton template + NPC yaml 필드 concat. 새로운 prose 합성 X.

**Connected work (hand-synth Round 3)**: 혜안 prose 는 Round 2 에 있음 → 그대로 yaml 이관. 수리공 / 어부 / 할머니 prose 는 신규 작성 — Sub-1 plan 의 첫 phase.

**Rejected**:
- 빌더 가 기존 필드 (`current_role_action` 등) 로 prose 합성 — paraphrase by builder, verbatim 원칙 위반.
- 모두 `rules/prompt_skeleton.yaml` 안 Jinja template 에 변수 채움 식 — NPC 별 prose 톤 다양성 손상 (혜안 시적, 수리공 건조 등).

### Decision 4 — 빌더 output 범위 = system prompt 전부 (history 제외)

**Context**: Round 2 손-합성 은 9 sections — 그러나 production prompt 는 `mechanic-spec.md` line 192-194 의 history / memory summary / current input + line 459 의 Layer 3 메타-디펜스 + surigong.yaml line 83-87 의 `hooks.system_prompt_variables` 까지 포함.

**Decision**: Sub-1 빌더 = system prompt 의 *정적/준정적* 전부 = Round 2 9 sections + Layer 3 메타-디펜스 + hooks variables. conversation history / running memory summary / current player input = Sub-2 (caller) 책임. OpenAI/Anthropic API 의 `system` (Sub-1) vs `messages` (Sub-2) 자연 경계.

**Rejected**:
- Round 2 9 sections 만 — Layer 3 누락 = mechanic-spec 위반.
- 다 포함 (history 까지) — Sub-1 ↔ Sub-2 경계 흐림, Sub-1 산출물 = "한 턴 의 전체 prompt" 가 되어 turn-by-turn orchestration 까지 끌어들임.

### Decision 5 — Snapshot oracle = 4-cell hand-synth (Round 3) + 16-cell property test

**Context**: 빌더 의 정답 (oracle) 은 *사람이 먼저* 작성. 그 방식 의 선택.

**Decision**: 4 cell verbatim snapshot + 16 cell property test 의 하이브리드.

**4 cell 분산** (모든 NPC 1번 + 모든 band 1번 노출):
- 수리공@0-30 (트로프 안 충실)
- 어부@30-60 (transaction 의 균열)
- 할머니@85+ (가장 오래 머문 자 의 자각)
- 혜안@60-85 (Round 2 그대로 이관)

**Property test 16 cell** (cross-product invariant):
- Layer 3 메타-디펜스 always present
- 현 band npc_tone verbatim 박힘
- 현 band sample_lines verbatim 박힘 (각 line)
- choice rule (`band.rule`) verbatim 박힘 — `band.rule` prose 가 choice_count 를 포섭 ("return EXACTLY N choices…"). 별도 numeric `choice_count:` 줄은 두지 않음 (승인된 4-cell oracle 에 없음). player_choice_tones 도 band 의 톤 정의로 박힘 (빈 band 85+ = "(없음 — 자유 입력)").
- persona_intro verbatim 박힘
- injected memory_tags ⊆ vocab

**Rejected**:
- 16 cell verbatim hand-synth — 12 cell 은 template-deterministic fill, 새 schema gap 노출 가능성 낮음. cost (3-5일) 대비 marginal value 낮음.
- 1 cell + property test 만 — verbatim 검증 약함, NPC 별 unique 결정 (예: 수리공 의 ruby hook) 커버 못함.

### Decision 6 — Schema validation = pydantic v2

**Context**: handoff 의 "pydantic / jsonschema" 미결정.

**Decision**: pydantic v2. 빌더 = Python only, Sub-2 FastAPI 가 pydantic 본거지 — 동일 의존성 재사용. cross-language 요구 없음 (jsonschema 의 portable schema 는 over-engineering).

## Architecture (3-layer)

```
┌─────────────────────────────────────────────────┐
│ 1. Schema layer (pydantic v2)                   │
│    npcs/*.yaml + rules/*.yaml → typed model     │
│    fail-fast on missing/invalid/enum            │
├─────────────────────────────────────────────────┤
│ 2. Render layer (Jinja2 StrictUndefined)        │
│    typed model + runtime state →                │
│    rules/prompt_skeleton.yaml 안 Jinja template │
│    → system prompt string (verbatim copy only)  │
├─────────────────────────────────────────────────┤
│ 3. Test layer (pytest)                          │
│    4-cell snapshot oracle + 16-cell property    │
└─────────────────────────────────────────────────┘
```

**Sub-1 ↔ Sub-2 경계**: Sub-1 = `system` 필드 의 string. Sub-2 = `messages` orchestration + history + LLM API + Postgres + Cloudflare + Layer 1/2/4 safety + Postgres 세이브 코드.

**spec-driven 3 원칙 ↔ 3 layer 매핑**:
- Closed vocab → Schema layer (pydantic enum, list-of-literal)
- 지시 vs 결과 → Render layer (yaml *지시* 박음, *결과 텍스트* 는 LLM 일)
- Verbatim → Test layer (snapshot diff = paraphrase 탐지)

## Data Flow

**Public API (caller 시점)**:

```python
from app.prompt_builder import build_prompt

system_prompt: str = build_prompt(
    npc_name="surigong",                   # "surigong" | "eobu" | "halmoni" | "hyean"
    awareness=70,                          # int 0-100
    memory_tags=["purpose", "regret"],     # list[str], subset of memory_tags vocab
    hooks_runtime={                        # NPC yaml 의 hooks.system_prompt_variables 채움
        "player_total_rubies_given_to_this_npc": 12,
    },
)
```

**내부 단계**:

```
1. loader.load_npc(npc_name) → NPCData
   • npcs/{name}.yaml 파싱 + pydantic 검증
   • 실패 → ValidationError throw at boot

2. loader.load_rules() → RulesData
   • rules/awareness_bands.yaml + memory_tags.yaml + boat_outcomes.yaml + prompt_skeleton.yaml
   • cache 가능 (rules 는 NPC 별 안 변함)

3. renderer.resolve_band(awareness, rules.awareness_bands) → BandSpec
   • awareness=70 → band [60, 85] cell 선택

4. renderer.build(npc, rules, band, memory_tags, hooks_runtime) → str
   • Jinja2 env (StrictUndefined) 에 변수 주입
   • prompt_skeleton.yaml 안 template 렌더
   • verbatim copy: yaml string → 출력 string

5. return system_prompt: str
```

**Edge case (spec-level, plan 에서 구체화)**:
- Band 경계: `[0, 30]` 의 30 = exclusive; 다음 band `[30, 60]` 의 30 = inclusive. `rules/awareness_bands.yaml` 에 명시. awareness=100 → band `[85, 100]` 의 100 = inclusive (마지막 band 특례).
- `memory_tags` 빈 list → `[Memory tags 누적]` section = `(empty)` 또는 section 생략. Round 3 hand-synth 의 0-30 cell 에서 검증.
- `hooks_runtime` 키 부족 (NPC yaml 명세 대비) → `ValueError("missing hook variable: <name>")` (renderer 단계 runtime contract — pydantic schema 무관). 키 잉여 → warning + ignore.

**NFR**:
- Latency: pure function, ~10ms 이내 expected.
- Determinism: 같은 입력 → 정확히 같은 출력.
- Memory: rules 캐싱 옵션 (Sub-2 의 turn loop 에서 의미).

## Error Handling

**원칙**: fail-fast, silent fallback X.

| 오류 | 발생 | 행동 |
|---|---|---|
| yaml 파일 누락 | loader | `FileNotFoundError` propagate |
| pydantic schema 위반 | loader 검증 | `pydantic.ValidationError` propagate (디테일 + 파일 경로 포함) |
| awareness ∉ [0, 100] | renderer.resolve_band | `ValueError("awareness out of range")` |
| band 경계 다중 match | renderer.resolve_band | `ValueError("ambiguous band boundary")` — rules yaml bug 신호 |
| Jinja2 undefined variable | renderer.build | `jinja2.UndefinedError` (StrictUndefined 모드) |
| hooks_runtime 키 부족 | renderer.build | `ValueError("missing hook variable: <name>")` |
| hooks_runtime 키 잉여 | renderer.build | warning log + ignore |

CLI 모드: 예외 → stderr traceback + exit code 1. library 모드: 예외 propagate.

## Testing

### Snapshot test (4 cell, verbatim)

```python
@pytest.mark.parametrize("npc,awareness,memory_tags,hooks,snapshot_file", [
    ("surigong", 15, [...], {...}, "surigong-band-0-30.txt"),
    ("eobu",     45, [...], {...}, "eobu-band-30-60.txt"),
    ("halmoni",  92, [...], {...}, "halmoni-band-85-100.txt"),
    ("hyean",    70, ["pattern","fear","loss"], {}, "hyean-band-60-85.txt"),
])
def test_snapshot(npc, awareness, memory_tags, hooks, snapshot_file):
    actual = build_prompt(npc, awareness, memory_tags, hooks)
    expected = Path("tests/prompt_builder/snapshots") / snapshot_file
    assert actual == expected.read_text()
```

Oracle = Round 3 hand-synth 4개 (수리공/어부/할머니 신규 + 혜안 Round 2 그대로 이관). 빌더 출력 ≠ oracle → fail.
Snapshot regenerate: `pytest --snapshot-update` (디자이너 가 의도적으로 yaml/template 변경 시만).

### Property test (16 cell invariant)

각 (NPC, band) cross-product 으로:
- `assert layer3_meta_defense_marker in output` — 메타-디펜스 항상 존재
- `assert npc.voice.awakening_bands[band_idx].npc_tone in output` — 현 band npc_tone verbatim
- `assert all(line in output for line in npc.voice.awakening_bands[band_idx].sample_lines)` — sample_lines verbatim
- `assert rules.awareness_bands.bands[band_idx].rule in output` — choice rule verbatim (rule prose 가 choice_count 포섭)
- `assert npc.identity.system_prompt_persona_intro.strip() in output` — persona prose verbatim (yaml `|` trailing newline 은 builder 가 trim)
- `assert all(tag in memory_tags_vocab for tag in injected_memory_tags)` — closed vocab

### Schema validation test

`tests/prompt_builder/test_schemas.py`:
- 의도적으로 깨진 yaml fixture → `pydantic.ValidationError` raise 검증
- 필수 필드 누락 / enum 위반 / 타입 mismatch 각 1 케이스
- 4 NPC 실제 yaml → validation pass (regression)

### CI / pre-commit hook (선택)

`scripts/check_yaml.py` 다음 단계 = `python -m app.prompt_builder.loader --validate-all`. pre-commit 훅에 연결 가능 — 디자이너 선택 (Phase 0 와 동일 의도 표명).

## Sequencing (high-level — plan 에서 milestone 화)

1. ADR 0022 / 0023 / 0024 작성 (결정 lock, audit trail 우선)
